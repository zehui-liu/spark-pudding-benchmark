| E2E-14 Iceberg 1.3 GiB full refresh | 10,000,000 | 25 s | 25 s | 1.55 GiB | 0 | PASS |
| E2E-14 Hudi 1.3 GiB full refresh | 10,000,000 | 244 s | 244 s | 4.69 GiB | 0 | PASS |

| E2E-06 10M MySQL CDC → Hudi | 10,000,013 | 4855 s | 3037 s | 8.68 GiB | 0 | PASS（行数） |
| E2E-06 10M MySQL CDC → Iceberg | 10,000,013 | 1021 s | 1021 s | 2.46 GiB | 0 | PASS |
| E2E-09 10M Kafka → Hudi | 10,000,000 | 1001 s | 195 s | 2.52 GiB | 0 | PASS |

说明：

- E2E-04 包含 10M 全量 bootstrap 和增量 2 insert/1 update 运行；wall time 覆盖两个 Spark
  应用。
- E2E-06 在快照完成且作业已流式 idle 后被 runner 的 4800 s 超时停止。数据完成时间由最后
  一个 Hudi commit 推导：作业开始 `20:36:44`，最后 commit `21:27:21`，即 `3037 s`。
  行数另外用 `table-check.sh hudi ... --count 10000013` 验证；runner 的 `cp` 路径 bug
  使作业本身成功后 wrapper 仍以 1 退出。
- 一个陈旧 inactive PostgreSQL replication slot 保留了 8.6 GiB WAL，导致第一次 E2E-04
  以 `No space left on device` 失败。删除 slot 后，成功运行使用相同的源/目标数据。
- E2E-06 首次只在 PostgreSQL 中遇到 `max_wal_size`/磁盘压力，而该用例不使用 PostgreSQL；
  实际运行使用 MySQL 和宿主机文件系统。
- E2E-09 的 producer 和流式作业在 Hudi commit `20261112000720160` 前完成写入；之后作业
  idle 直到被停止。有效完成时间从首个 Hudi commit 计算，不包含 idle 等待。
- E2E-14 Hudi/Paimon scale 模板是为该基线新增的。两者都新建 10M 行表，不像 Iceberg scale
  用例那样替换已有 200 行表。
- E2E-06 Iceberg scale 需要预先创建 Iceberg 表（`create-iceberg-table.sh`）和连续 trigger；
  流式 sink 拒绝无界 MySQL CDC source 的 `available-now`。Iceberg `total-records` 达到
  10,000,013 后立即停止，因此 1021 s 是数据完成时间，不是 idle 超时。
