# spark-pudding-benchmark

English | [简体中文](README.md)

A local single-node end-to-end test and benchmark project for `spark-pudding`. It verifies the
correctness, recovery behavior and scale characteristics of the `v1.0.0` release across real
Spark, JDBC, CDC, Kafka, lakehouse and object-storage combinations.

Current companion versions:

```text
spark-pudding  v1.0.0
Project        1.0.0
Development    1.0.1-SNAPSHOT
```

## Version alignment

This project follows the `spark-pudding` release tags.

| spark-pudding | spark-pudding-benchmark |
| --- | --- |
| `v1.0.0` (current tag) | `1.0.0` |
| `1.0.1-SNAPSHOT` (development) | `1.0.1-SNAPSHOT` |
| `v1.0.1` (next tag) | `1.0.1` |

Rules:

- The current version tracks the latest release tag: `v1.0.0` maps to `1.0.0`;
- When `spark-pudding` moves to the next development version, bump this project too;
- Drop `-SNAPSHOT` at release time and align with the new tag;
- A version bump must update:
  - `spark-pudding-benchmark/VERSION`
  - version numbers in README and RELEASE documents
  - distribution paths and runtime jar versions in `config/env/` and `scripts/`
  - version examples under `docs/`;
- This project follows `spark-pudding` only and is not coupled to other projects.

## One-command run

Run the complete `1.0.0` benchmark (preflight, smoke, scale preparation, scale gates
and report):

```bash
scripts/run/bench-suite.sh all
```

The first run generates `data/seed` deterministically. Phases can also be run separately:

```bash
scripts/run/bench-suite.sh preflight   # environment, version and disk checks
scripts/run/bench-suite.sh smoke       # P0 smoke
scripts/run/bench-suite.sh prepare     # generate and load scale data
scripts/run/bench-suite.sh scale       # E2E-01/04/06/09/14 scale gates
scripts/run/bench-suite.sh report      # summarize the latest suite
scripts/run/bench-suite.sh cleanup     # stop all Docker profiles
```

Common options:

```bash
scripts/run/bench-suite.sh all --dry-run          # print commands only
scripts/run/bench-suite.sh all --keep-services    # keep services running
scripts/run/bench-suite.sh prepare --force-data   # regenerate scale data
scripts/run/bench-suite.sh scale --run-id <id>    # reuse a specific run id
```

Reports:

```text
results/bench/suite-<run-id>/report.md
results/bench/benchmark-report.md       # latest report
```

A full run needs enough Docker Desktop memory, about 30 GB of disk and serial profile
execution; it usually takes hours depending on the host. The quick start below is the
manual, step-by-step path for debugging individual cases.

## Scope

This is not a production load-testing platform. It is a repeatable **regression test bed**:

- Validate the batch, sync and streaming job modes;
- Validate source, transform and sink combinations and dependency checks;
- Validate JDBC/MySQL/PostgreSQL/MongoDB CDC, Kafka, Schema Registry and lakehouse writes;
- Validate incremental state, locks, fencing tokens, checkpoint restart and failure recovery;
- Validate object storage, table maintenance, capability manifests and negative error paths;
- Collect comparable wall time, driver RSS, spill and input-throughput baselines on a
  single-node Docker environment.

It does not promise:

- Multi-node execution, production data volumes or real SLAs;
- The same resource isolation and network conditions as a production cluster;
- Long-running soak tests;
- Full benchmark execution in GitHub Actions.

## Relationship to spark-pudding

Default layout:

```text
own-code/
├── spark-pudding/              project under test
└── spark-pudding-benchmark/    this test bed
```

The job files, Docker services and data-generation scripts in this project are not written into
the `spark-pudding` repository. Tests use the
`spark-pudding/build/target/spark-pudding-<version>/` distribution by default, or an unpacked
release pointed to by `PUDDING_HOME`.

## Quick start

> For the complete benchmark, use `scripts/run/bench-suite.sh all`. The steps below are the
> manual path for debugging a single case or phase; `bench-suite.sh` manages profiles, data
> preparation and the final report automatically.

### 1. Prerequisites

- JDK 11 (recommended) or JDK 17;
- Maven 3.8+;
- Docker Desktop with at least 8 GiB memory and 30 GiB free disk;
- Python 3.10+;
- Spark 3.4.0;
- A `spark-pudding` distribution.

### 2. Build the project under test

```bash
cd ../spark-pudding
mvn -B clean verify
```

Artifacts:

```text
spark-pudding/build/target/spark-pudding-1.0.0/
spark-pudding/build/target/spark-pudding-1.0.0.tar.gz
```

### 3. Prepare the environment

```bash
cd ../spark-pudding-benchmark

# Docker service configuration; up.sh also creates this on first use
cp config/docker/.env.example config/docker/.env

# Spark/Pudding paths
cp config/env/env.example.properties config/env/env.local.properties
chmod 600 config/env/env.local.properties
```

Edit `config/env/env.local.properties`:

```properties
JAVA_HOME=/path/to/jdk-11
SPARK_HOME=/path/to/spark-3.4.0-bin-hadoop3
PUDDING_HOME=/path/to/spark-pudding-1.0.0
```

Load it into the current shell:

```bash
set -a
source config/env/env.local.properties
set +a
```

### 4. Start services

Start one profile at a time to avoid exhausting Docker Desktop memory:

```bash
scripts/services/up.sh relational    # PostgreSQL, MySQL, MongoDB
scripts/services/up.sh streaming     # Kafka, Schema Registry
scripts/services/up.sh search        # Elasticsearch
scripts/services/up.sh infra         # MinIO, Redis, etcd
scripts/services/up.sh hdfs          # NameNode, DataNode

scripts/services/status.sh
```

Switch profiles:

```bash
scripts/services/down.sh relational
scripts/services/up.sh streaming
```

### 5. Load smoke data

The large `data/seed` files are not committed; generate them on first use
(fixed seed 42, 100,000 rows):

```bash
python3 scripts/data-gen/01_generate_tables.py \
  --profile smoke --out data/seed --formats csv,jsonl --force
```

Then load them:

```bash
scripts/services/up.sh relational

PUDDING_DATA_DIR="$PWD/data/seed" PUDDING_DATA_CONTAINER_DIR=/data-seed \
  scripts/data-gen/03_load_postgres.sh
PUDDING_DATA_DIR="$PWD/data/seed" PUDDING_DATA_CONTAINER_DIR=/data-seed \
  scripts/data-gen/04_load_mysql.sh

scripts/data-gen/setup-python.sh
.venv/bin/python scripts/data-gen/05_load_mongo.py \
  --data-dir data/seed --tables orders,customers,payments
```

`/data-seed` is the read-only mount of `data/seed`; `data/generated` remains mounted at `/data`.

### 6. Run one case

```bash
# Single case
scripts/run/run-case.sh E2E-01 --dataset smoke

# File/Hive/transform smoke, no lakehouse data required
scripts/run/run-smoke-suite.sh file-basic smoke

# One-command smoke: loads seed and manages relational/streaming/search
scripts/run/bench-suite.sh smoke
```

`run-case.sh` renders `config/jobs/*.yaml`, substitutes data paths and submits the job through
the bundled client. The required Docker profile is case-specific; see the script header.

### 7. Generate scale data and run scale cases

Use the orchestrator:

```bash
scripts/run/bench-suite.sh prepare   # generate/check scale data, load PG/MySQL, prepare Iceberg
scripts/run/bench-suite.sh scale     # E2E-01/04/06/09/14 scale gates
scripts/run/bench-suite.sh report    # unified report
```

Run one benchmark case manually:

```bash
python3 scripts/data-gen/01_generate_tables.py \
  --profile scale --out data/generated --formats csv,jsonl --force

scripts/run/bench-case.sh E2E-04-scale --rows 10000002 \
  --result-case E2E-04-scale -- scripts/run/run-e2e.sh E2E-04-scale

scripts/run/bench-summary.py results/bench
```

`bench-case.sh` collects wall time, Spark event metrics, driver RSS and Docker resource samples
under `results/bench/<case>-<timestamp>/`; `bench-suite.sh report` writes
`results/bench/suite-<run-id>/report.md` and `results/bench/benchmark-report.md`.

### 8. Stop services

```bash
scripts/run/bench-suite.sh cleanup
```

Or stop profiles individually:

```bash
scripts/services/down.sh relational
scripts/services/down.sh streaming
scripts/services/down.sh search
scripts/services/down.sh infra
scripts/services/down.sh hdfs
```

## Test coverage

### Functional dimensions

| Dimension | Coverage |
| --- | --- |
| Job modes | batch, sync full/incremental, streaming |
| Sources | file, Hive, JDBC, MySQL/PostgreSQL/MongoDB CDC, Kafka, Elasticsearch, lakehouse |
| Transforms | filter, column, aggregate, join, union, dedup, limit, validate, schema contract |
| Sinks | file, Hive, JDBC, MySQL, Hudi, Paimon, Iceberg, Kafka, MongoDB, Elasticsearch |
| Incremental semantics | append, upsert, CDC, cursor, fencing token, lock and transaction recovery |
| Streaming | checkpoint restart, watermark, window aggregation, stream-stream join, state TTL |
| Object storage | S3A checkpoint/state, Iceberg S3FileIO, HDFS, credential isolation |
| Operations | checkpoint CLI, state CLI, capabilities, table maintenance, maintenance-server |
| Error paths | multiple sinks, dependency cycles, missing keys/schema/secrets, invalid CDC op, no credential leaks |
| Scale | 1.3 GiB transform, 10,000,000-row JDBC, 10M CDC, 10M Kafka |

### Test layers

| Layer | Content |
| --- | --- |
| P0 smoke | Minimal runnable paths for components and capabilities, 30/30 PASS |
| E2E | E2E-01 through E2E-15: transforms, CDC, Kafka, lakehouse, full refresh, round trips |
| SR/SK | Source/sink combination matrix |
| OS | Object storage, checkpoint/state, HDFS, table maintenance, maintenance-server, capabilities |
| RG | kill -9, concurrent locks, pending transactions, Kafka/MySQL restarts, checkpoint cleanup |
| NG | Multiple sinks, unknown dependencies, dependency cycles, invalid modes, missing fields/secrets, invalid CDC ops |
| Scale | E2E-01/04/06/09/14 scale gates |

### Pass criteria

- The job exits with code 0, or the case-specific effective-completion condition is met;
- Target row counts, contents and checkpoint/state assertions pass;
- No duplicates after a checkpoint restart;
- Error messages name the offending keys and do not contain credential values;
- Scale cases record the distribution hash, Spark event logs and resource samples.

## Current benchmark results

Single-node macOS, JDK 11, Spark 3.4.0 `local[2]`, Docker Desktop on the same host. See
[RELEASE.en.md](RELEASE.en.md) for the environment, process and limitations.

| Case | Rows | Wall | Effective completion | Peak RSS | Result |
| --- | ---: | ---: | ---: | ---: | --- |
| E2E-01 1.3 GiB transform | 10 output rows | 23 s | 23 s | 1.05 GiB | PASS |
| E2E-14 Iceberg 1.3 GiB full refresh | 10,000,000 | 25 s | 25 s | 1.55 GiB | PASS |
| E2E-14 Hudi 1.3 GiB full refresh | 10,000,000 | 244 s | 244 s | 4.69 GiB | PASS |
| E2E-14 Paimon 1.3 GiB full refresh | 10,000,000 | 27 s | 27 s | 1.48 GiB | PASS |
| E2E-04 10M PostgreSQL incremental | 10,000,002 | 163 s | 146.3 s + 6.8 s | 4.77 GiB | PASS |
| E2E-06 10M MySQL CDC to Hudi | 10,000,013 | 4855 s | 3037 s | 8.68 GiB | PASS |
| E2E-06 10M MySQL CDC to Iceberg | 10,000,013 | 1021 s | 1021 s | 2.46 GiB | PASS |
| E2E-09 10M Kafka to Hudi | 10,000,000 | 1001 s | 195 s | 2.52 GiB | PASS |

These are local regression baselines, not production SLAs. Compare only on the same host,
Spark memory, Docker profile and data profile; investigate wall-time regressions above 20% or
peak-RSS regressions above 25%.

## Known limitations

- Single-node Docker environment; run only one heavy profile at a time;
- E2E-06 Hudi 10M CDC is a long job; the default runner timeout is 80 minutes;
- Hudi/Paimon 10M full refresh creates new tables; the Iceberg scale case needs a pre-created table;
- PostgreSQL may retain WAL through an inactive replication slot; clean stale slots before a 10M write;
- The MinIO test image is pulled from `quay.io/minio/minio`; `minio/minio` is no longer available on Docker Hub;
- Benchmark numbers apply only to the current host and distribution and are not production capacity planning inputs.
